AI MCP DEPLOYMENT PROJECT ROADMAP
=================================

Document purpose
----------------
This document is the primary implementation roadmap for building and deploying:

1. A remote Model Context Protocol (MCP) server written in TypeScript.
2. A separate AI client application that connects to the MCP server.
3. A production-ready deployment workflow that goes beyond localhost.
4. Supporting infrastructure for authentication, persistence, observability, testing, and CI/CD.

This file is designed to be referenced repeatedly by an AI coding assistant. Each phase includes:

- Objective
- Why the phase matters
- Detailed implementation steps
- Suggested technologies
- Expected outcomes
- Completion criteria
- Common mistakes
- Optional extensions

The project should be completed incrementally. Do not build every advanced feature at once. The priority is to create a working end-to-end path early, then improve it safely.

======================================================================
1. PROJECT GOAL
======================================================================

Primary goal
------------
Build an AI-powered operations assistant consisting of two independently deployed services:

A. MCP Server
   - Exposes well-defined tools.
   - Validates inputs.
   - Executes business logic.
   - Returns structured results.
   - Enforces authorization.
   - Records tool execution logs.

B. AI Client
   - Provides a user interface.
   - Sends user requests to a language model.
   - Presents MCP tools to the model.
   - Receives model-generated tool calls.
   - Invokes the remote MCP server.
   - Displays tool activity and results.
   - Requires approval for sensitive actions.

The main learning objective is deployment engineering, not advanced AI research.

Core skills this project should teach
-------------------------------------
- TypeScript and Node.js
- MCP server and client development
- Remote HTTP-based service communication
- API design
- Docker
- Container networking
- Managed cloud deployment
- Environment variables and secrets
- PostgreSQL
- CI/CD
- Authentication and authorization
- Logging, metrics, and tracing
- Failure handling
- Infrastructure as code
- Optional Kubernetes deployment

Recommended project theme
-------------------------
Remote AI Operations Assistant

The client allows a user to ask questions such as:

- "Is the image-processing service healthy?"
- "Show me recent failed deployments."
- "Search logs for timeout errors."
- "Create a high-severity incident."
- "Generate an incident summary."
- "What changed in the last deployment?"

Suggested initial MCP tools
---------------------------
1. get_service_status
2. list_services
3. list_deployments
4. get_deployment_details
5. search_logs
6. create_incident
7. list_incidents

The first version should implement only three tools.

- Protects model API keys.

3. PROJECT RULES
======================================================================

Rule 1: Build a vertical slice early
------------------------------------
The first working version should support:

User input
  -> AI client
  -> model decides to call a tool
  -> MCP client calls MCP server
  -> MCP server runs tool
  -> result returns to model
  -> answer appears in UI

Do not wait until authentication, PostgreSQL, or Terraform are complete before testing this flow.

Rule 2: Keep AI logic simple
----------------------------
The project exists to learn deployment.

Avoid spending most of the project on:
- Complex multi-agent routing
- Advanced retrieval systems
- Large prompt frameworks
- Custom model training
- Vector databases
- Fine-tuning

Use a single model and a small number of reliable tools.

Rule 3: Use strict TypeScript
-----------------------------
Enable strict mode.

Recommended tsconfig settings:
- strict: true
- noImplicitAny: true
- noUncheckedIndexedAccess: true
- exactOptionalPropertyTypes: true
- noFallthroughCasesInSwitch: true

Do not use "any" unless documented and unavoidable.

Rule 4: Validate all external data
----------------------------------
Use Zod or an equivalent runtime validation library.

Validate:
- Environment variables
- HTTP request bodies
- Tool inputs
- Tool outputs
- Database records when needed
- External API responses
- Model-generated arguments

TypeScript types alone do not validate runtime data.

Rule 5: Treat model output as untrusted
---------------------------------------
A language model can generate:
- Invalid arguments
- Dangerous arguments
- Hallucinated tool names
- Excessively large values
- Repeated operations
- Requests outside the user's permissions

Every tool call must pass validation and authorization.

Rule 6: Separate read tools and write tools
-------------------------------------------
Read tools may run automatically.

Write tools should require user approval.

Examples of write tools:
- create_incident
- deploy_service
- delete_log
- restart_service
- send_message
- update_database_record

Rule 7: Never store production state in a container filesystem
--------------------------------------------------------------
Containers are replaceable and ephemeral.

Use:
- PostgreSQL for persistent application data
- Object storage for files
- Redis only when temporary shared state is needed
- Managed secret storage for secrets

7. PHASE 3 - DESIGN MCP TOOLS
======================================================================

Objective
---------
Define reliable tool contracts before implementing the MCP server.

Tool design principles
----------------------
Each tool should:
- Have one responsibility.
- Have a clear name.
- Have a precise description.
- Use a strict input schema.
- Return a structured result.
- Have documented errors.
- Have bounded inputs.
- Have a timeout.
- Avoid hidden side effects.
- Declare whether approval is required.

Tool 1: get_service_status
--------------------------
Purpose:
Return current status information for one service.

Input:
{
  "serviceName": "string"
}

Output:
{
  "serviceName": "string",
  "status": "healthy | degraded | unhealthy | unknown",
  "version": "string",
  "lastDeployment": "ISO_DATE",
  "checkedAt": "ISO_DATE"
}

Possible errors:
- SERVICE_NOT_FOUND
- INVALID_SERVICE_NAME
- STATUS_PROVIDER_UNAVAILABLE

Approval:
Not required.

Tool 2: search_logs
-------------------
Purpose:
Search recent logs for a service.

Input:
{
  "serviceName": "string",
  "query": "string",
  "limit": 1 to 100,
  "startTime": "optional ISO_DATE",
  "endTime": "optional ISO_DATE"
}

Output:
{
  "serviceName": "string",
  "query": "string",
  "count": "number",
  "entries": [
    {
      "timestamp": "ISO_DATE",
      "level": "info | warn | error",
      "message": "string",
      "requestId": "optional string"
    }
  ]
}

Possible errors:
- SERVICE_NOT_FOUND
- INVALID_TIME_RANGE
- LOG_PROVIDER_UNAVAILABLE
- QUERY_TOO_LONG

Approval:
Not required.

Tool 3: create_incident
-----------------------
Purpose:
Create an incident record.

Input:
{
  "serviceName": "string",
  "severity": "low | medium | high | critical",
  "summary": "string",
  "details": "optional string"
}

Output:
{
  "incidentId": "string",
  "status": "created",
  "createdAt": "ISO_DATE"
}

Possible errors:
- SERVICE_NOT_FOUND
- INVALID_SEVERITY
- DUPLICATE_INCIDENT
- DATABASE_UNAVAILABLE

Approval:
Required.

Tasks
-----
1. Define Zod schemas for all tool inputs.
2. Define Zod schemas for all tool outputs.
3. Define error codes.
4. Define approval metadata.
5. Define timeouts.
6. Define maximum input sizes.
7. Add example inputs.
8. Add example outputs.
9. Add contract tests.
10. Add documentation for tool behavior.

Expected outcome
----------------
The tool contract is clear enough that another developer can implement the tool without asking what it should do.

Completion criteria
-------------------
- Every tool has a Zod input schema.
- Every tool has a Zod output schema.
- Every tool has example data.
- Every write tool is marked as requiring approval.
- Every field has a clear meaning.
- Limits are documented.
- Error responses use a consistent shape.

Recommended error shape
-----------------------
{
  "error": {
    "code": "SERVICE_NOT_FOUND",
    "message": "The requested service does not exist.",
    "retryable": false,
    "requestId": "req_123"
  }
}

Common mistakes
---------------
- Tool names such as run_operation or execute_action.
- Returning plain unstructured text for everything.
- Using one large tool with many unrelated operations.
- Allowing unlimited result sizes.
- Using optional fields when they should be required.
- Changing schemas without versioning.

10. PHASE 6 - BUILD THE AI CLIENT BACKEND
======================================================================

Objective
---------
Create a backend service that combines an LLM with the MCP client.

Responsibilities
----------------
The AI client backend should:
- Receive user chat messages.
- Load available MCP tools.
- Convert MCP tools into the model's tool format.
- Send the request to the model.
- Detect tool calls.
- Validate tool arguments.
- Determine whether approval is required.
- Invoke the MCP server.
- Send tool results back to the model.
- Return the final answer.
- Record tool activity.
- Enforce a maximum number of tool iterations.
- Enforce timeouts.
- Track model usage.

Suggested request flow
----------------------

1. User sends message.
2. Backend loads conversation.
3. Backend requests available MCP tools.
4. Backend filters tools based on user permissions.
5. Backend sends message and tool definitions to model.
6. Model returns either:
   a. Final answer
   b. Tool call
7. Backend validates tool call.
8. Backend checks approval requirement.
9. For read tool:
   - Execute tool automatically.
10. For write tool:
   - Return pending approval state.
11. After tool result:
   - Send result back to model.
12. Model creates final answer.
13. Backend stores messages and tool records.
14. Backend returns response to UI.

Important safety controls
-------------------------
- Maximum tool calls per user message.
- Maximum tool result size.
- Model timeout.
- MCP timeout.
- Allowed tool names.
- User permission checks.
- Approval requirement.
- Input validation.
- Output validation.
- Request ID propagation.
- Token usage limits.

Suggested project structure
---------------------------

apps/web-client/lib/
|
|-- ai/
|   |-- model-client.ts
|   |-- tool-loop.ts
|   |-- prompt.ts
|   `-- usage.ts
|
|-- mcp/
|   |-- client.ts
|   |-- tool-adapter.ts
|   |-- tool-cache.ts
|   `-- errors.ts
|
|-- auth/
|-- approvals/
|-- conversations/
|-- config/
`-- logger/

Minimum backend endpoints
-------------------------
POST /api/chat
POST /api/tool-approvals/:id/approve
POST /api/tool-approvals/:id/reject
GET /api/health
GET /api/mcp-status

Suggested response states
-------------------------
- completed
- pending_tool_approval
- failed
- timed_out

Example pending approval response

  "status": "pending_tool_approval",
  "approvalId": "approval_123",

    "name": "create_incident",
    "arguments": {
      "serviceName": "image-processing-api",
      "severity": "high",
      "summary": "Repeated timeout errors"
    }
  }
}

Expected outcome
----------------
The backend can accept a natural-language message and execute a read-only MCP tool selected by the model.

Completion criteria
-------------------
- The model receives tool schemas.
- The model selects get_service_status for an appropriate question.
- Tool arguments are validated.
- The MCP server receives the call.
- The tool result is returned to the model.
- The user receives a final answer.
- Write tools stop at pending approval.
- Tool loops are limited.
- Errors are logged.
- Model usage is recorded.

Common mistakes
---------------
- Allowing the model to call any arbitrary tool name.
- Trusting model arguments without validation.
- Sending sensitive environment variables to the model.

16. PHASE 12 - TOOL APPROVAL AND IDEMPOTENCY
======================================================================

Objective
---------
Prevent accidental or duplicate execution of state-changing tools.

Approval flow
-------------
1. Model requests create_incident.
2. Backend validates arguments.
3. Backend creates pending tool execution.
4. Backend creates approval record.
5. UI displays approval request.
6. User approves.
7. Backend atomically marks approval approved.
8. Backend executes tool once.
9. Backend stores result.
10. UI displays outcome.
11. Repeated approval click returns existing result.

Idempotency
-----------
Every write tool call should have an idempotency key.

Example:
incident-create:user_123:conversation_456:toolcall_789

The MCP server should:
- Check whether the key already exists.
- Return the previous result when repeated.
- Avoid creating a second incident.

Tasks
-----
1. Add approval table.
2. Add pending execution state.
3. Add approve endpoint.
4. Add reject endpoint.
5. Add idempotency key generation.
6. Add database uniqueness constraint.
7. Add transaction around approval and execution claim.
8. Add duplicate click handling.
9. Add expiration for stale approvals.
10. Add tests for concurrent approvals.
11. Add tests for network retry.
12. Add tests for duplicate request.

Expected outcome
----------------
A write tool executes at most once, even if the user clicks twice or the network retries.

Completion criteria
-------------------
- Approval is required for create_incident.
- Rejected tools never execute.
- Duplicate approval does not duplicate the action.
- Expired approval cannot execute.
- Idempotency keys are stored.
- Concurrent requests are handled safely.

Common mistakes
---------------
- Executing the tool before storing approval state.
- Using only frontend button disabling.
- Automatically retrying write tools.
- No unique constraint.
- Treating model tool-call ID as globally unique without checking.

- Tool loop cannot run forever.

- No jitter.
- Outer timeout shorter than inner operation.
- Health endpoint always returns success.
- Swallowing provider errors.
- Crashing on malformed model output.
- No user-facing error state.

======================================================================
26. VERSIONING STRATEGY
======================================================================

Tool schema versioning
----------------------
Prefer backward-compatible changes.

Safe changes:
- Add optional field.
- Add new tool.
- Add new output metadata.
- Improve description without changing meaning.

Breaking changes:
- Rename required field.
- Remove field.
- Change field type.
- Change tool semantics.
- Change error behavior.

Breaking-change options:
1. Add a new tool name such as get_deployment_v2.
2. Version the MCP endpoint.
3. Support old and new schema during migration.
4. Coordinate client and server deployment.

Application versioning
----------------------
Expose:
- Git commit SHA
- Semantic version
- Build timestamp
- Environment

Recommended endpoint:
GET /version

Example:
{
  "version": "1.2.0",
  "commit": "a18d53f",
  "builtAt": "ISO_DATE",
  "environment": "production"
}

Expected outcome
----------------
You can identify exactly what code is running and avoid incompatible deployments.

7. Keep MCP tool registration separate from business logic.

11. Use structured errors.
12. Use structured logging.

16. Do not automatically retry non-idempotent operations.
